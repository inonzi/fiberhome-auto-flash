# 源码级验证：天海/华邦 ECC 错配导致变砖的交叉比对报告

## 1. 项目溯源与数据来源
本报告旨在对比**烽火原厂固件**与**开源 U-Boot 源码**中的闪存控制器参数差异，以查明 HG5585F 系列机型（搭载华邦、天海、铠侠等闪存）出现“刷机变砖”的底层原因。

### 1.1 项目来源信息
*   **官方主线基础**：[pbs05/uboot-an758x](https://github.com/pbs05/uboot-an758x) (当前本地 `main` 分支)
*   **华邦临时修复版**：由 GitHub 用户 [xe5700/uboot-an758x-winbond](https://github.com/xe5700/uboot-an758x-winbond) 基于官方主线构建。
*   **修复版核心提交**：`db01535c` (nand: add temporary Winbond 8-bit migration build)、`40ee7872`、`8528c96a`。

### 1.2 数据提取源
1. **原厂写入数据**：提取自 `NAND-ECC-问题报告.md` 第 3.1b 节中解包的 `vendor_kernel.bin` 原厂内核 NAND 配置表。
2. **开源读取数据**：提取自本地 `uboot-an758x` 仓库源码 `tf-a/plat/ecnt/common/drivers/flash/parallel_nand_flash_table.c`。

## 2. 原厂（Vendor）固件配置表
原厂在出厂烧录内核中，对主板上混用的多款 2Gbit 闪存颗粒配置如下（`soc_ecc` 列即实际读写使用的 ECC 位数）：

| ext_id (芯片ID) | 厂商与型号 | min_ecc | **soc_ecc (原厂设定)** |
| :--- | :--- | :--- | :--- |
| `0x589591` | **华邦 (Winbond)** W29N08GVSIAA | 1 | 4 |
| **`0x069510`** | **华邦 (Winbond)** W29N02KVSIAF | 4 | **8** |
| `0x049580` | **美光 (Micron)** MT29F01G08ABAEA | 4 | 4 |
| `0x069590` | **旺宏 (MXIC)** MX30LF2G18AC | 8 | 12 |
| `0x64a690` | **美光 (Micron)** MT29F08G08ABACA | 8 | 12 |
| `0x762691` | **铠侠 (Kioxia)** TC58NVG4S0HTA20 | 8 | 12 |
| **`0x761590`** | **铠侠 (Kioxia)** TC58NVG1S3HTAI0 | 8 | **8** |
| **`0x469590`** | **天海 (Skyhigh)** S34ML02H200TFI000 | 4 | **8** |
| **`0x469500`** | **天海 (Skyhigh)** S34ML02G300TFI00 | 4 | **8** |

*事实：原厂对华邦、铠侠、天海的主力 2Gbit 颗粒，实际写入均采用了 **8-bit** 配置。*

## 3. 开源 U-Boot 源码配置表
从 `uboot-an758x` 源码 `main` 分支提取的 TF-A/BL2 层配置（最后一位数字为 `soc_ecc_ability`）：

| ext_id | 源码中的型号 | 源码设定的 **soc_ecc** | 对比结果 |
| :--- | :--- | :--- | :--- |
| `0x589591` | **华邦** W29N08GVSIAA | 4 | 一致 |
| **`0x069510`** | **华邦** W29N02KVSIAF | **4** | ❌ **不一致** (原厂为8) |
| `0x049580` | **美光** MT29F01G08ABAEA | 4 | 一致 |
| `0x069590` | **旺宏 / 美光** | 4 / 12 | 一致 |
| `0x64a690` | **美光** MT29F08G08ABACA | 12 | 一致 |
| `0x762691` | **铠侠** TC58NVG4S0HTA20 | 12 | 一致 |
| **`0x761590`** | **铠侠** TC58NVG1S3HTAI0 | **8** | ✅ **一致 (正常读取)** |
| **`0x469590`** | **天海** S34ML02H200TFI000 | **4** | ❌ **不一致** (原厂为8) |
| **`0x469500`** | **天海** S34ML02G300TFI00 | **4** | ❌ **不一致** (原厂为8) |

*(注：U-Boot 源码 `nand_ids.c` 中的 `NAND_ECC_INFO` 同样将这几款芯片标记为了 4)*

## 4. 事实结论

通过上述两表的数据对比，可以得出以下客观结论：

1. **为何铠侠未受影响？**
   铠侠 (TC58NVG1S3HTAI0) 在原厂写入配置与开源 U-Boot 读取配置中，均被设定为 8-bit，写读一致，因此运行正常。
2. **为何华邦与天海变砖？**
   开源 U-Boot 源码中为这两款芯片设定的读取参数为 4-bit，而原厂实际写入格式为 8-bit。BL2 和 U-Boot 在启动时使用 4-bit 逻辑去解析 8-bit 数据，发生校验错位，导致无法加载镜像。
3. **问题本质**
   这是开源代码配置与特定整机厂商（烽火）实际部署参数之间的不匹配。根源在于上游源码未包含针对此整机环境的 8-bit 写入格式数据。

## 5. 修复方向
通过引入华邦修复版的 `CONFIG_AIROHA_NAND_ECC_BRIDGE` 机制（将 ECC 覆盖为 8），并将天海颗粒的 ID (`0x01 0xda...`) 加入匹配白名单，即可实现：
*   让天海芯片与铠侠一样，以 8-bit 方式读取原厂数据。
*   保留 `nandecc 4` 的运行时切换指令，防止未来刷入仅支持 4-bit 格式的固件时无法回退。
